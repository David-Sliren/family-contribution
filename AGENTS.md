# AGENTS.md

Next.js 16 App Router app (package `contribution-aleida`) for a family contribution platform. Plain JavaScript/JSX, no TypeScript; Tailwind v4. UI copy and all repo conventions are in Spanish.

## Documentación
- Documentación para desarrolladores con el esquema Diátaxis en `docs/` (índice en `docs/README.md`): `tutorials/`, `how-to/`, `reference/` y `explanation/`. No duplicar allí lo que ya cubre este archivo; lo que es "por qué" vive en `docs/explanation/`.
- `DESIGN.md` documenta el sistema de diseño (paleta M3, tokens) y `.agents/skills/README.md` indexa las skills del proyecto.

## Commands
- Package manager is **pnpm** (`pnpm-lock.yaml`). Use `pnpm dev` / `pnpm build` / `pnpm start`.
- `pnpm lint` (= `eslint`, flat config in `eslint.config.mjs`) and `pnpm lint:fix`. There is **no test suite and no typecheck** — lint is the only automated verification.

## Layout & data flow
- Alias `@/*` → `src/*`.
- Backend: `src/app/api/**/route.js` → static classes in `src/models/*.js` (DB connect + business rules + role checks) → mongoose schemas in `src/database/*.js`. Cached connection via `src/utils/mongoose-helper/db.js` (throws without `MONGODB_URI`).
- Validation is duplicated on purpose: zod backend schema (export `...SchemaBanckend`, e.g. `userBackendSchema`) and a frontend one (export `...Fronted`). Only `contribution.frontend.js` is a separate file; `user/patient/inventory/expense` keep both exports in the same file. Server-controlled fields (`createBy`, `updateBy`, `paymentId`) are injected server-side and deliberately omitted from frontend schemas. Keep that split. Auth forms use `src/schemas/login.js` and `userFrontedSchema`.
- Frontend data layer is per feature: `src/services/<feature>/config.js` (axios instances) + `<feature>.js` (methods). Errors are thrown through `getServiceError` (`src/services/error.js`), matching the `.error`/`.message` keys routes return.
- TanStack Query wrappers in `src/hooks/tanstack/{query,mutation}`; query hooks export `queryOptions` usados por las páginas para prefetch en servidor + `HydrationBoundary` (el layout del dashboard solo pre-fetchea `main-patient`).
- UI state via zustand (`src/store/`): only `store/ui/notifications.js` and `store/medicineStore.js` (the old `store/user/userStore.js` was deleted). Dashboard filters/pagination are URL state with `nuqs` (see inventory toolbar).
- Manual API probes live in `src/requests/**/*.rest`; `src/app/api/[...not-found]/route.js` returns a 404 JSON for unmatched API paths.
- Route handlers use async params: `const { id } = await params`.

## Patient & contribution model
- Ya **no existe `userId`** en patient/contribution: los campos son `createBy` (quién crea/aporta) y `updateBy` (quién actualiza), inyectados por las rutas desde la sesión. `contribution` además exige `patientId` (required), que `POST /api/dashboard/contributions` inyecta con el paciente principal.
- **Crear contribuciones es solo-admin**: `POST /api/contributions` ya no existe (la ruta quedó solo-GET); el create vive en `POST /api/dashboard/contributions` (sesión + `role === "admin"`, exige `createBy` — puede ser el mismo admin —, inyecta `patientId`/`updateBy`). Los usuarios normales aportan a su nombre **únicamente por la pasarela de pago** (webhook → `Contribute.create`), nunca por API. `createContribution` (`services/contribution`) apunta a `/api/dashboard/contributions`; `AddContributionDialog` conserva el usuario destino tras el éxito (`reset({ createBy: user.id })`).
- `patient` (`src/database/patient.js`) usa virtuales de colección + getters derivados, eficientes con **un solo populate** en `Patients.getById` (`.populate("funds").populate("totalInventories").populate("expenses")`):
  - `funds` (ref Contribution, `match: { status: "confirmado" }`) y `expenses` (ref Expense); `totalInventories` (count).
  - Getters `totalFunds` (suma), `monthFunds` (conteo del mes), `totalExpenses`/`monthExpenses` (sumas) leen `this.funds`/`this.expenses` — sin populate devuelven 0 (no lean el parámetro del getter).
- `funds` y `expenses` **no se envían al frontend**: el schema encadena su propio `toJSON.transform` sobre el de `cleanIdPlugin`, que **pisa** cualquier transform previo (`cleanDatabase.js` hace spread y reasigna `transform`) — si añades otro, envuélvelo después del `plugin(cleanIdPlugin)`. Los totales sí se serializan.
- `/api/main-patient` elige el paciente con `isMain: true` (fallback al primero), lo resuelve con `getById` y devuelve los totales poblados. `MetricsGrid` (dashboard) y `Stats` (home) leen esos totales para "Fondo disponible" (`totalFunds − totalExpenses`), gastos y aportes del mes.
- **`/contribute` (pública) usa selector de método de pago**: dos tarjetas con descripción — "Transferencia" (`TransferPanel.jsx`: teléfono Nequi y `keyT` del paciente principal con botón copiar; **solo informativo, NO registra contribución**) y "Pasarela de pago" (formulario de Mercado Pago existente, mantiene su requisito de sesión → 401 con usuario anónimo). `FormContribute`, `InfoContribute` (muestra nombre y apellido del paciente principal en el copy) y `TransferPanel` leen el paciente con `useMainPatientQuery` (GET público `/api/main-patient`); `components/contribute/Index.jsx` envuelve ambos bloques en `Suspense`/`ThreePoints`.
- **Un solo paciente principal (`isMain`)**: `Patients.create` lo marca `true` si nadie lo es aún (el primer paciente queda principal); `Patients.setMain` (`PUT /api/dashboard/patients/[id]/main`, solo admin) quita el `isMain` de los demás (`updateMany $ne id`) y lo pone al objetivo. La opción "Hacer principal" vive en el popover de `PatientCard` (se oculta si ya es principal).
- El campo de imagen de `user`/`patient` es **`image`** (nomenclatura Better Auth), no `img`.
- **`tel` y `keyT` son requeridos en `patient`**: `tel` (teléfono Nequi, misma validación que el usuario: exactamente 10 dígitos empezando por 3) y `keyT` (clave transacional Bre-B, texto no vacío) viven en `patientSchema` (zod), así que el schema de alta/edición (`patientSchemaFrontend`) **obliga a rellenarlos al crear o editar** un paciente; `patientUpdateSchema` (`.partial()`) los deja opcionales para no romper updates como solo `{ image }`. En mongoose van con `default: ""` y **sin `required`** a propósito (documentos legados no fallan al guardar). `PatientCard` los muestra con botón copiar (clipboard + notificación del store) y `Add/UpdatePatientDialog` los incluyen como `FieldType`.
- `Patients.getAll(querys, paginate)` devuelve **`{ data, pagination }`** (patrón server-pagination, ver skill `dashboard-filters-pagination`): los llamadores que quieren la lista completa deben destructurar `.data` (`/api/main-patient` y `/api/contributions` lo hacen) y `limit: 0` (default del modelo) = sin límite. `GET /api/dashboard/patients` acepta `page`/`limit`/`search` (regex insensible sobre `name` y `lastName`). `patientUpdateSchema` es `.partial()` para updates parciales (p.ej. solo `{ image }`).
- El virtual `contributions` de `user` (`src/database/user.js`) usa `foreignField: "createBy"` y alimenta `totalContributed`/`monthMoreActive` (perfil, stats, UserCard).
- Las mutaciones de contribution/inventory/expense (además de patient) invalidan la query `main-patient` en `onSuccess` (`src/hooks/tanstack/mutation/`) para que las métricas se actualicen tras cada acción.
- **Fondo para gastos**: `Expenses.create`/`update` rechazan si `amount > totalFunds − totalExpenses` (paciente con populate de `funds`/`expenses`; en update se suma el monto actual del gasto). Error `INSUFFICIENT_FUNDS` → 400 en `/api/dashboard/expenses` con mensaje en inglés (los errores del backend van en inglés); `AddExpenseDialog`/`UpdateExpenseDialog` validan antes con los totales de `main-patient` y muestran "Fondo disponible" en el form (copy en español).

## Eventos
- Colección `event` (`src/database/event.js`): `type` (`contribution|inventory|expense`), `action` (`creado|actualizado|eliminado`), refs (`entityId`, `patientId`, `createBy` = actor), `description` y `amount`. zod en `src/schemas/event.js` (`eventBackendSchema` / `eventFrontedSchema`).
- `Events.register` (`src/models/event.js`) compone la descripción en el servidor con `formatMoney` (`src/config/money.js`), valida con zod y **nunca rompe** la mutación principal (try/catch + `console.error`, devuelve `null`). Se invoca desde `Contribute`/`Expenses`/`Inventories` en create, update y delete — `Contribute` no tiene delete —; el webhook de pago queda cubierto porque llama a `Contribute.create`.
- `GET /api/events` paginado (`page`/`limit`/`type`) **sin chequeo de sesión**, igual que los demás GET de lista: el prefetch SSR hace self-fetch sin cookies y lo rechazaría con 401. La UI queda protegida por el proxy en `/dashboard`.
- Frontend: `services/event/` + `useQueryEvent` (queryKey `["events"]`); las mutaciones de contribution/inventory/expense invalidan `["events"]` en `onSuccess`.
- `ActivityTimeline` (dashboard home) es client con `useSuspenseQuery`; `home/Index.jsx` lo envuelve en `Suspense`/`ThreePoints` y `dashboard/page.jsx` pre-fetchea con `HydrationBoundary`.

## Organización de componentes y archivos
- Ruta por feature: `src/app/(home)/<feature>/page.jsx`; dashboard: `src/app/(home)/dashboard/<feature>/page.jsx`.
- **Pages livianas**: importan `Index` de `@/components/<feature>/Index`, definen `titleData` (home) o `metadata` (dashboard) con title/subtitle/description y, en dashboard, pre-fetchean con `...QueryOptions` + `HydrationBoundary`. No llevan JSX de UI.
- **Componentes de la feature aplanados** en `src/components/<feature>/` (sin subcarpetas por pantalla) y con prefijo de la feature en PascalCase:
  - `Index.jsx` → `export const Index = ({ title, subtitle, description })`; compone layout genérico + filtros/toolbar + `Suspense`/`ThreePoints` + lista + dialogs. "Index" es el componente de sección, **NO un barrel**: no existen archivos `index.js` de re-export.
  - `<Feature>List.jsx` o `<Feature>Grid.jsx`: lista cliente con URL state `nuqs` (page + `GlassPaginationBasic`) y query de TanStack.
  - `<Feature>Card.jsx`: tarjeta de item individual.
  - `Add<Feature>Dialog.jsx` / `Update<Feature>Dialog.jsx`: modales CRUD.
  - `patients` hoy es un **grid** (no tabla): `PatientGrid` + `PatientCard` + `PatientImageDialog`. `TablePatiens.jsx` queda sin uso (conservado a propósito). El diálogo de imagen monta `CoverUpload` (`src/components/ui/avatar/CoverUpload.jsx`), variante ancha de `AvatarUpload` para la foto del paciente: valida con `fileImageFronted`, sube al folder `cover` (`FOLDER_IMAGES[1]`, 960×1280) y persiste con `updatePatient(id, { image })`; tiene botón Cancelar (`ButtonVariant` `secundary` con `commandfor`).
- **Layouts genéricos**: `PageLayout` en `src/components/ui/layout/` (home, usa `Title`) y `DashboardShell` en `src/components/dashboard/layout/` (dashboard, header eyebrow+title+description); ambos con firma `({ title, subtitle, description, className, children })`.
- Utilidades del dashboard en `src/components/dashboard/ui/` (bar/Toolbar, chips/Chip).
- Excepciones al aplanado: `auth/login/Login.jsx` y `auth/register/Register.jsx` viven en subcarpeta, igual que los subárboles de `profile/`. El proveedor está en `src/components/provaider/` (typo histórico de "provider").
- Solo `page.jsx` usa default export; el resto usa `export const`. Nombres con prefijo de feature se distinguen por ruta (ej. `InventoryCard` en home y en dashboard).

## Auth
- **Better Auth** (`better-auth` + adaptador `better-auth-mongoose`), ya no se usa JWT con `jose`.
- Server config en `src/utils/auth.js`: `mongooseAdapter(mongoose.connection, { adoptExistingModels: true })` reutiliza el modelo mongoose `User` (`src/database/user.js`); `additionalFields` agrega `tel`, `relationship` y `role` (`role` con `input: false`, o sea controlado por servidor); `emailAndPassword` habilitado; plugin `username()`; `socialProviders` con Google (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`); `cookiePrefix: PREFIXTOKEN` (`"family-contribution"` en `src/constants/config.js`).
- **Username autogenerado**: `databaseHooks.user.create.before` → `beforeRegisterHook` (`src/utils/hooksAuth.js`). Si el registro no trae `username` (p. ej. alta vía Google), lo genera con un slug del nombre/email (sin acentos, ≤20 chars, mínimo 3), agrega sufijo aleatorio de 4 dígitos ante colisión (hasta 5 intentos) y setea `displayUsername`. El registro por correo sí lo pide el formulario, así que el hook no interviene ahí.
- Cliente en `src/utils/auth-client.js` (`createAuthClient` con `BASE_URL` + `usernameClient()`). Login llama `authClient.signIn.username` y registro `authClient.signUp.email`; no quedan rutas `api/auth/login|register|logout` escritas a mano.
- Handler catch-all `src/app/api/auth/[...all]/route.js` (`toNextJsHandler(auth)`).
- Sesión en servidor: `getSession` en `src/utils/getUserData.js` = `cache(() => auth.api.getSession({ headers: await headers() }))`. Las rutas leen `session.user.id`/`session.user.role` para inyectar campos y verificar rol (mutaciones de `/dashboard` exigen `role === "admin"`).
- `src/proxy.js` (Next 16 renombró middleware→proxy) usa `getSession()`; matcher: `/inventory`, `/expenses`, `/profile`, `/auth/:path*`, `/dashboard/:path*`, `/api/dashboard/:path*`. Sin sesión → JSON 401 en `/api/*` y redirect `/` en páginas; con sesión en ruta de auth → redirect `/`; no-admin en dashboard → 403/redirect. **Blindaje de mutaciones del dashboard**: `/api/dashboard/*` pasa por el proxy pero los `GET` se eximen del chequeo de sesión (`isDashboardRead`) porque el prefetch SSR hace self-fetch sin cookies; solo las mutaciones (POST/PUT/DELETE) exigen sesión+admin en el proxy (los route handlers repiten el chequeo como defensa en profundidad).
- Sesión en cliente: `AuthProvider` (`src/components/provaider/`, ojo con el typo) recibe la sesión del server; `useUserStore()` **ya no es un store de zustand** y devuelve `{ user, isAuth, isPending, logout }` respaldado por `authClient.useSession()` (su argumento `selector` hoy se ignora).
- Mongoose schema plugin `cleanUser` en `src/utils/mongoose-helper/cleanDatabase.js` mapea `_id`→`id` y elimina campos privados.
- **Verificación de correo obligatoria** (`requireEmailVerification: true` + `emailVerification` con `sendOnSignUp`/`sendOnSignIn` en `src/utils/auth.js`): el registro ya **no crea sesión** — `Register.jsx` envía `callbackURL: "/auth/verify-email"` y muestra "Revisa tu correo"; el login sin verificar responde `EMAIL_NOT_VERIFIED` (manejado en `Login.jsx`; Better Auth reenvía el enlace con cada intento). La página `/auth/verify-email` (`components/auth/verify-email/VerifyEmail.jsx`) muestra éxito cuando la query no trae `error`, o el motivo (`INVALID_TOKEN`, `TOKEN_EXPIRED`, `USER_NOT_FOUND`, `INVALID_USER`). ⚠️ **Migración en producción**: los usuarios existentes necesitan `emailVerified: true` (`updateMany`) o no podrán iniciar sesión; además, con verificación activa Better Auth responde genérico ante correos duplicados (la rama `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL` de `Register.jsx` ya no dispara).
- **Recuperación de contraseña**: `emailAndPassword.sendResetPassword` en `auth.js`; `Login.jsx` enlaza a `/auth/forgot-password` (`ForgotPassword.jsx` → `authClient.requestPasswordReset` con `redirectTo: "/auth/reset-password"`; responde siempre `status: true`, anti-enumeración) → Better Auth envía `/api/auth/reset-password/:token?callbackURL`, que redirige a `/auth/reset-password?token=` (`ResetPassword.jsx` → `authClient.resetPassword` con `{ newPassword, token }`); token inválido/expirado redirige con `?error=INVALID_TOKEN`. Schemas `forgotPasswordSchema` y `resetPasswordSchema` en `src/schemas/login.js`.

## Correos transaccionales
- `src/utils/email.js` es **solo servidor** y exporta `sendEmail({ toEmail, subject, template })`: renderiza `TemplateEmail` (`src/components/ui/email/TemplateEmail.jsx`) con `renderToStaticMarkup` y lo envía por SMTP de Gmail con `nodemailer` (puerto 465, `secure: true`; credenciales `GMAIL_USER`/`GMAIL_APP_PASSWORD` leídas desde `src/constants/env.js`). El import de `react-dom/server` es **dinámico** (`await import(...)`) porque el estático lo bloquea Turbopack.
- `TemplateEmail` usa **estilos inline a propósito**: el HTML de correo no procesa Tailwind ni clases externas (Outlook borra los `<style>`, Gmail recorta selectores); mantiene la paleta M3 de DESIGN.md en hex y es reutilizable para cualquier correo (verificación, recuperación, futuros avisos). Los fallos de envío **no rompen ningún flujo**: Better Auth los captura en `runInBackgroundOrAwait` y solo loguea `Failed to run background task`.
- Consumida hoy por los callbacks `sendVerificationEmail` y `sendResetPassword` de `src/utils/auth.js`.

## Env / payments
- Requires `.env` (renombrado desde `.env.local`; ver `.env.example`): `MONGODB_URI`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `BASE_URL`, `MP_ACCESS_TOKEN`, `GMAIL_USER`, `GMAIL_APP_PASSWORD`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `NEXT_PUBLIC_GA_ID`.
- Lee las variables con `src/constants/env.js`, nunca `process.env` en línea. `BASE_URL` cae a `VERCEL_URL` y `MP_ACCESS_TOKEN` se expone como `ACCESSTOKEN_MP` (`src/constants/payment.js`).
- MercadoPago checkout in COP; min amount 6000 se valida solo en los schemas zod (se quitó el chequeo extra de la ruta). `BASE_URL` feeds the webhook and back URLs, so local payment testing needs a public tunnel (an ngrok origin is in `allowedDevOrigins` of `next.config.mjs`). Approved payments create a Contribution via `src/app/api/payment/webhook/route.js` (duplicate `paymentId` is ignored, error 11000).
- ⚠️ **Pendiente**: el webhook aún construye la contribution con `userId` y sin `patientId`/`createBy`, así que falla contra el schema actual — la pasarela de pago quedó fuera de los cambios y hay que arreglarla aparte (mapear `external_reference.userId` → `createBy` e inyectar `patientId`). No se tocaron archivos de `src/app/api/payment/`.
- Only `res.cloudinary.com` is allowed in `next.config.mjs` remote images. `pnpm-workspace.yaml` `allowBuilds` gates native deps (bcrypt, sharp, unrs-resolver) — new native deps may need an entry there.
- The `.opencode/` folder is an unrelated npm project (OpenCode plugin dep), not the app; leave its own `package.json`/lockfile alone.
